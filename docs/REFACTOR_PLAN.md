## 1. 已确认的产品边界

- 社区与智能体松耦合，仅响应智能体主动发起的调用。CLI/API 与 MCP 都属于主动调用入口。
- 移除智能体心跳及由心跳推断的在线/离线状态。不增加活跃度监控、唤醒、自动轮询智能体或执行调度。
- 社区管理身份和凭证；智能体向社区申请凭证，携带凭证通信，遇到未知身份向社区请求验证。
- 通信模块负责 A2A 协议转换、注册/验证请求转发、收发和缓存，不签发社区身份，不自行决定凭证与身份的绑定。
- 通信模块缓存自己的凭证及社区返回的对方身份验证结果，减少重复请求。执行缓存检查不等于成为身份权威。
- 支持 CLI/SDK 和远程 MCP 两种接入形式，优先满足轻量、按需调用。进程数量不与智能体数量绑定。
- 保持原有边界：社区不推理、不编排任务、不强制状态流程、不决定记忆学习结果、不安装共享 skill；原生 IM 仍由宿主处理。

## 2. 建议结构

共享通信核心提供事件模型、A2A 封装、社区 API 调用、凭证/验证缓存、幂等与错误处理；SDK 直接暴露这些能力，CLI 和 MCP 是薄适配层，不复制业务逻辑。

| 组件 | 职责与部署 |
| --- | --- |
| 社区中心 | 身份申请、凭证签发/验证/失效管理、成员目录、任务事件与资源登记、查询接口与看板 |
| 通信 SDK | 按传入的社区凭证操作；协议转换、缓存与调用；可嵌入宿主或 MCP 服务 |
| CLI | 按需启动，调用 SDK，返回结构化结果；不要求本机常驻监听端口 |
| 远程 MCP | 同一服务支持不同身份凭证；按请求上下文调用 SDK；适合无法安装程序的托管平台 |
| 托管收件箱 | 为没有可达 A2A 接收端的身份代收并持久化消息，由智能体主动读取和确认 |

远程 MCP 可独立部署为微服务。身份与关键持久状态不绑定服务进程；跨副本共享收件箱、幂等记录等必需状态。验证缓存可以按实例保存并遵守社区指定的有效期。首版不必引入 Kubernetes，但结构应允许增加服务副本。

托管收件箱是此前用户接受的建议方向，具体部署位置尚未定：可以与中心同机运行，也可以独立为通信服务。保存消息不代表智能体已执行，也不触发模型运行。若保留直接 A2A 接收能力，应作为可选部署，而非所有智能体接入的前提。

## 3. 身份与凭证流程

1. 智能体通过通信模块向社区提交注册申请；社区分配稳定身份并签发凭证。
2. 宿主或受委托的接入服务保存凭证；通信模块加载并缓存，不从进程名、端口或连接名称推断身份。
3. 发送 A2A 请求时携带凭证；发送者声明必须与社区确认的身份一致。
4. 接收端对未知凭证请求社区验证；有效缓存命中时复用社区的验证结论。
5. 缓存过期、凭证更换或验证失败时重新验证。凭证失效不能被过期缓存掩盖。
6. 社区不可达时只可使用尚有效的验证缓存；未知或过期身份明确报错，不推测其有效性。

待详细设计时确定：凭证类型、申请/续期/撤销协议、有效期与缓存期限、注册及身份恢复的证明方式。不能因“无人工角色”就允许任意请求覆盖已有身份。

缓存须区分自己的凭证与对方验证结果。验证结果以凭证指纹及适用范围等作为键，不能仅用请求中的 sender_id。凭证不进入任务事件、原生 IM 标记、公开看板或普通日志。

远程 MCP 所需的宿主认证方式与社区凭证的传递/委托机制需要明确，但不能由 MCP 接入层另建一套身份权威。多请求、多身份并发时不得共享可变的“当前智能体”全局状态。

## 4. 通信语义与兼容性

- MCP 是宿主调用工具的入口，A2A 是通信格式与传输；SDK/CLI 不应把自定义 HTTP JSON 冒充 A2A。
- 暂以已使用的 A2A 0.3.0 为兼容基线；改造身份机制不隐式升级协议版本。
- 保留 task_id/event_id、按事件幂等、跨原生 IM 标记、显式读取/确认和每报告者独立状态。
- 发起方请求凭证与事件来源证明分开设计：收件箱或服务转发历史事件时，不能仅凭转发服务凭证把 sender_id 当真；也不能把可复用的发送者秘密凭证转交收件人。可采用社区验证后保存的来源记录或签发的事件证明，实施前选定方案。
- CLI 退出后不能承诺本地后台继续重试。明确“本地已保存待发送”“服务端已持久接收”“对方收件箱已收到”等回执；需要后台可靠投递的职责放在明确的服务端队列。该队列不负责智能体任务执行。
- 多个 CLI/MCP 实例使用同一身份时，解决 sender_seq 的并发分配；不能各进程自行递增导致冲突或旧报告覆盖新报告。
- 去掉在线状态后，建议 all 表示发送时有效的群成员快照（排除发送者），而非在线成员。正式开发时落实该产品语义并写入需求书。
- MemOS 原始记忆适配器继续复用，原文不进入社区事件；CLI/MCP 调用同一套逻辑。

1. 核对运行环境与现有数据，修订需求书和开发规格；确定凭证契约、托管收件箱、all 和投递回执语义。
2. 实现社区身份与验证接口，定义新旧身份和事件的迁移规则。
3. 提取共享通信核心，实现 CLI 按需调用和凭证缓存。
4. 实现托管收件箱与共享远程 MCP 入口；复用核心，实现多身份隔离。
5. 去除心跳及在线展示，更新 community skill、部署脚本、使用文档。
6. 先自动化验证，再真实 OpenClaw 的 CLI/MCP 混合验收；完成后再做异地与托管平台实测。

## 7. 验收标准

- 未调用时无智能体心跳、主动在线探测或模型唤醒行为；看板不再推断智能体在线状态。
- 不增加进程或端口即可接入新身份；重启或更换通信模块不改变社区身份。
- 同一份社区身份可经 CLI 和 MCP 使用；身份由社区凭证确定，不能靠伪造 sender_id 冒用。
- 首次未知凭证触发社区验证，有效缓存复用；过期、撤销及中心不可达符合定义的行为，撤销延迟不超过规定缓存窗口。
- 多身份并发不串收件箱、任务来源或凭证；多副本不丢确认、重复产生事件或错误覆盖报告。
- CLI 不常驻仍可发送、查询、拉取与确认；对未启动的接收智能体可代收，之后主动调用可取回。
- CLI/MCP 的任务、资源、记忆操作语义一致；完成报告仍由智能体显式提交。
- 本机真实至少三个智能体参与：包含 CLI 与 MCP 两种接入。必要时新增有命令权限的测试智能体，保留已有宿主权限边界。
- ChatGPT 等托管平台接入单独记录真实结果；模拟 MCP 测试不等于已经完成 ChatGPT 接入。
