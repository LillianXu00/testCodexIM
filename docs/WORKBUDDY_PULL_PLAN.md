# WorkBuddy 主动拉取接入：改造评估

状态：后端已实现为独立适配器 0.1.0。本文保留设计评估，最终接口与部署以 [实现说明](../adapters/workbuddy/README.md) 为准。中心目录保持原接口，pull 模式由适配器持久保存并通过配置工具查询；未新增中心专属字段。真实 WorkBuddy 原生定时任务尚待宿主侧接入验收。

## 1. 职责与消息路径

采用 WorkBuddy 原生定时任务驱动一次有界收件回合。项目不安装 cron、不建立宿主 hook、不创建模型轮询或唤起 WorkBuddy 的服务。

发送智能体 → 发送通信节点持久出站队列 → WorkBuddy 指定的共享通信节点持久收件箱。
WorkBuddy 原生定时任务 → 通信 MCP → 领取本人待处理消息 → 自主处理／回复／确认。
发送与接收节点独立向中心旁路登记任务和事件。看板不成为消息中转站。

“发送后只需登记就返回”落实为：持久接受投递后就向发送者返回，不等待 WorkBuddy 上线、拉取或执行。单独写入看板事件不能保证消息可领取，必须有持久收件或待投递队列。现有发送工具已先持久入队并返回 queued_at_sender；跨节点投递失败仍应显示待重试/失败，不能冒称收件成功。

这里的共享通信节点是已有 MCP 服务，不是 WorkBuddy 本机新增进程。它被调用时提供收件数据，不主动执行“替 WorkBuddy 拉取”的任务。已有节点投递队列重试与宿主定时收件是两件事。

## 2. 已有能力与缺口

| 当前能力 | 评估 |
| --- | --- |
| 自由注册并签发本人凭证 | 可复用，不需要入会令牌 |
| 远程 MCP 凭证认证 | 可复用，WorkBuddy 只能操作自己的收件箱 |
| 持久 inbox 和事件去重 | 可复用，节点重启不丢消息 |
| a2a_get_unread_messages | 可读取本人未确认消息，但读取与领取分离，且按最早记录截断，长期领取项可能挤占批次 |
| community_claim_event | 有原子领取，但只有永久 claimed 标志，没有消费租约与持有人标识 |
| a2a_ack_messages / community_release_event | 有确认/释放，但尚未按租约校验当前消费批次 |
| a2a_publish_task / a2a_reply_task | 已异步入队，可保留任务、事件与回复引用 |
| 宿主自动接入 | 当前 receive 默认建立 host 作业，pull 模式必须明确禁用，不能以 host 失败/uncertain 充当拉取模式 |
| 地址登记 | 当前要求接收 URL，pull 模式需由共享节点提供接收地址，不能要求 WorkBuddy 虚构入口 |

## 3. 建议改造的接口和记录

以下是建议名称与契约，不是已发布 API：

1. `community_configure_delivery(mode="pull")`：本人凭证认证，明确选择代收节点。共享节点登记自己的 A2A 代收地址和身份绑定，将目录 receive_mode 设为 pull；返回节点、模式与持久接收状态。无需 WorkBuddy 公网 URL。无参数查询或独立查询接口可检查生效状态。对 push/native 身份保持原行为。
2. `a2a_pull_messages(limit=20, consumer_id, lease_seconds=...)`：一次调用原子获取并领取本人的可处理消息，返回验证后的 event、领取凭据、租约到期时间和 has_more。只返回本身份消息，不接受工具参数指定其它身份。空箱立即返回；MCP 不长轮询等待新任务。
3. 确认/释放工具兼容扩展：pull 路径携带领取凭据，校验本人、event_id、当前租约和持有人；过期旧回合不能确认新回合的领取。成功处理后 ack，失败释放需先核对外部副作用。现有 push 路径的调用参数不被无故破坏。
4. 接收处理根据持久 receive_mode 决定是否创建 host 作业。pull 模式只验证、存储、旁路记录，不调用 OpenClaw 或 WorkBuddy，不产生虚假的 host 失败。
5. 目录和回执显示接收方式及投递状态：queued_at_sender、stored_for_pull、claimed、acknowledged 与智能体主动报告的任务状态分开。不能因为长时间未拉取就判断智能体离线或任务失败。

pull 工具应复用签名和社区证明验证，不能仅信任 sender_id。节点入站已验证并保存的消息可在拉取时输出 verified event，无需智能体再次将同一历史消息交给 decode。若只返回原始 envelope，必须定义证明过期/撤销后的历史验证语义，避免已经持久接受的消息因证明过期而永远无法处理。

## 4. 必须同时处理的边界

- **消息类型**：拉取聊天、任务、报告/回复全部社区消息，不能只拉 TASK_PUBLISH，否则任务发起者收不到迟来的答复。优先级是选项，不应丢弃其他类型。
- **重叠调度**：原生定时任务尽量不重叠；服务端仍要有原子领取，避免手动运行与定时运行抢到同一消息。
- **中断恢复**：租约过期并不证明业务没执行过。重新领取应标记 redelivery，由智能体核对自身记忆、task_id/event_id、已发回复和外部副作用；不宣称 exactly-once。
- **回复幂等**：回复成功后 ack 丢失不能重复发布新回复。先保留稳定回复 event_id 和请求参数，重试沿用；必要时查询任务历史进行核对。
- **状态语义**：领取不是执行完成，ack 不是 COMPLETED。长任务可先报告实际进展；租约续期策略需与单次执行预算一致，不引入中心任务调度。
- **批次与积压**：单轮设置条数和执行时长上限，有积压留待后续回合。避免无限循环清空箱子，也不能让已领取未完成的前 N 条阻塞后续消息。
- **停用与清理**：WorkBuddy 长期不运行时保留待处理消息；存储上限、到期/归档策略需可见，不能静默丢弃。停止宿主定时任务不等于注销社区身份。
- **安全范围**：MCP 连接使用个人凭证，不用看板查询令牌；不能跨身份领取或确认。任务内容仍是外部输入，不自动获得企业微信或其它外部操作权限。
- **凭证与工具刷新**：凭证过期会导致定时任务认证失败，应提示维护而非不断重注册；工具升级后宿主可能需要刷新 MCP 工具列表。
- **切换模式**：从 push/native 切换 pull 时，已有 host 作业须核对是否已受理，不能无条件回放。首版建议 WorkBuddy 使用新身份，并按身份独立设置，现有四个智能体保持原模式。
- **同一节点**：拉取、领取、回复和确认使用同一共享通信服务，保留回复原事件的上下文。不同副本不能使用相互独立的 SQLite 收件箱冒充一个节点。

## 5. 验收

1. 注册 WorkBuddy 身份，无公网入口也可启用 pull；不修改现有四个身份。
2. WorkBuddy 不运行时，其他智能体发任务立即获得入队回执，消息在代收箱持久保存，中心旁路记录可查，不出现 host 执行作业。
3. 定时任务启动后只能领取自己的消息；空箱立即结束。
4. 两次调度并发不重复领取；进程重启后消息仍在；过期领取可恢复且明确提示重复风险，旧领取凭据不能确认新租约。
5. WorkBuddy 回复原任务，另一智能体按原接入路径收到；WorkBuddy 发任务后的回复也能由后续定时回合领取。
6. ack、回复和入站重复重试保持幂等；毒消息/超时不使整个批次永久卡住。
7. 两个独立节点的代收投递与中心短暂不可用下的重试语义如实报告。
8. 最后由真实 WorkBuddy 原生定时任务触发两轮执行，验证不是测试脚本或项目后台替它启动。

## 6. 专用交付物

`agent_connect_workbuddy/` 从 `agent_connect/` 复制后修改，保留自由注册、MCP、CLI/SDK、MemOS 与资源能力。移除了强制公网入口的接入要求，并明确仅 WorkBuddy 原生定时任务可周期拉取。私密 MemOS Key 不复制：本模式首选远程 MCP，使用服务端 MemOS 项目配置即可。

当前可先安装 skill、注册身份、配置 MCP 并使用主动发送/查询工具；后端 pull 模式与原子批量领取尚未实现时，不创建宣称收件就绪的定时任务。`examples/scheduled-task-prompt.md` 提供开发上线后的原生任务提示词，无宿主专用 cron/hook 命令。
